# MysteryAtHome workflow

Apply only to the MysteryAtHome repository. Follow its [AGENTS.md](../../../AGENTS.md), including Slovak communication and the existing Site publishing workflow.

- Before starting each new user task, briefly summarize your understanding in Slovak and ask whether it may proceed (for example, "Môže to tak byť?"). Wait for the user's explicit confirmation before implementing that task. If the user corrects the summary, confirm the revised understanding first. Once confirmed, complete the agreed scope, including its required commit, push, and publication, without requesting the same approval again.
- Treat mobile phones as the primary device for both the sales page and gameplay. Design and visually check these experiences on phone-sized screens first: readable text, comfortable touch controls, proportionate media, and a coherent composition of images, text, and actions. A desktop layout or a check for horizontal overflow alone is not enough to establish mobile quality. For example, preserve the opening illustration's visual impact with text over the image on phones instead of separating it into a large dark text block followed by the image.
- Preparation, storyboard, and Game Master are primarily desktop workflows for the parent and developer. Optimize them for computer use; their phone layout has lower priority than the sales page and gameplay. Preserve a good desktop presentation while prioritizing phone quality in the player-facing experience.
- When changing a task, keep its storyboard, printable worksheet, parent instructions and downloadable PDFs synchronized in the same task. Use the shared content in `print-materials.js` and game answers from `game-data.js`; regenerate affected PDFs/previews and the combined bundle, and check that instructions, clues and solutions agree. The parent guide is the first printable page and should remain a readable single A4 covering the introduction and every task.
- Work only on `main`. Do not create feature branches or push changes to another branch.
- After each completed task that changes repository files, commit the task's changes with a descriptive message and push to `origin/main`. The user has explicitly authorized this workflow; do not ask again for routine commits and pushes.
- If the Sites source helper creates commits, reuse them and push them to `origin/main` too. A push to the Sites source repository does not replace the GitHub push.
- Verify the push succeeded before reporting completion. Reconcile remote changes without force-pushing or discarding user work. If a push remains blocked, report the blocker accurately.
- After every completed change, including instructions and skills, include a clickable Markdown link to the permanent deployed Site in the final response. The user wants to click it and open the preview in a new browser tab; use a supported new-tab handoff when available. Browser-tab behavior of chat links depends on the client, so do not promise a forced new tab without tool support. Never substitute localhost or a temporary Codespace URL. Current Site URL: https://zahada-u-vas-doma.alert-coin-6330.chatgpt.site. Use the latest returned deployment URL if it changes.
- Read-only actions do not need an empty commit. Do not commit secrets or unrelated work.

## Pixelkovia artwork and localization

- The user selected character set B: friendly living electronic components in the original soft painted pixel style. Preserve the original blue cloud-headed Piko with his screen face, suit and teal tie. Plugy uses the approved USB-shaped design with arms and legs, but without the cable tail or its extra connector; apply this consistently in portraits and group scenes.
- Never generate or bake a concrete character name into any illustration, including portraits, funnel images, task scenes, the book, worksheets and other printable artwork. Keep names and localizable captions in editable HTML or printable text outside the bitmap. Do not hide an old nameplate with an HTML overlay: the image itself must contain no character name.
- Newly written or revised text intended for recording, voiceover or TTS must not mention any concrete character name, including self-introductions, direct addresses and references to another character. Use natural pronouns or simple descriptions of the character's function instead. Check the entire spoken script before recording; visible editable character headings may still use names. Preserve existing recordings until their replacement is explicitly in scope.
- The adventure takes place in a human apartment. For the requested funnel direction, show a recognizable ordinary living room behind the digital characters gathered around a glowing digital table; use the approved group composition as a reference rather than replacing the apartment with a digital fortress.

## Mobile audio — all sounds in this project

- Apply the Šutko playback approach to every new or changed sound, including voice messages, video sound and sound effects where applicable. Preserve requested automatic playback after success. Initiate playback and unlock Web Audio synchronously within a real tap/click/submit handler; never rely on a fresh, unprepared `play()` call from a delayed callback. For a reveal such as Šutko’s nine, prime the same media element during the final correct tap through a Web Audio gain of zero, keep it active and connected through the reveal/render, then rewind to the beginning and release the gain when the result appears. Restore temporary looping and release the audio context when leaving. Do not use the media `muted` attribute as a substitute for gesture authorization. Keep a manual play fallback if the browser denies sound; page loads, QR navigation and reloading an already completed task must not initiate unsolicited sound.
- Silently preload recordings while the player solves the task. Use the real asset with a supported format, matching extension and HTTP MIME type (MP3: `.mp3`, `audio/mpeg`), and `playsinline` for media elements. Retain the same buffered element across the task/result render and clean up old event listeners.
- Provide a clear play/pause/resume/replay control. Report audible playback only after `playing`; distinguish loading, paused, ended and failed states. Handle rejected `play()` promises: `NotAllowedError` leaves a manual play action; a media/network failure leaves a retry that reloads the failed source. Keep the transcript available for voice messages without opening it automatically on failure.
- Pause and release sound when leaving its screen. Playback, errors and retries must preserve saved progress and must not advance the game.
- Verify audio changes with the actual shipped recording and real touch interactions in mobile Chromium (Pixel/Android) and WebKit (iPhone), using normal autoplay policies. Synthetic tones may supplement these checks but cannot replace the recording. Check silent preloading/reveal, gesture priming, automatic audible start from the beginning at the result without another tap, retained buffer, pause/resume/replay, leaving during the reveal, denied playback and recovery after a failed request. Follow `tests/sutko.test.cjs` and `tests/kvak-audio.test.cjs` as existing examples. Report any verification limit; emulator playback alone does not prove the cause of noise on a physical phone.
